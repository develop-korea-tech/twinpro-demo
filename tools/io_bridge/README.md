# TWIN PRO 연결 프로그램 (io_bridge)

현장 장비 값을 읽어 TWIN PRO 서버 입구(`tp_ingest_signal`)로 보내는 프로그램입니다. 화면 5개는 이 입구로 들어온 신호를 실시간으로 반영합니다.

## 1. 무엇을 하는 프로그램인가

### 1-1. 신호가 들어오는 두 경로

| 경로 | 장비 | 통신 | 읽는 값 |
|---|---|---|---|
| 개별 장비 직결 | LS XGT 계열 PLC(설비마다 1대) | Modbus TCP, 포트 502 | Coil 00001 = 가동(1) / 정지(0), DI 10001 = 이상(1), HR 40001 = 누적 생산 수량 |
| 집약 라우팅 장비 경유 | AC&T ETOS 통신 서버(여러 설비를 RS-485 등으로 모음) | XGT FEnet(IP), 포트 2004 | 설비마다 %MW 3개: 가동(0/1) · 누적 수량 · 이상(0/1) |

설비별 경로와 주소는 화면 **기준정보 → 수집 포인트** 탭, 서버 표 `tp_io_point`에 있습니다. 지금 들어 있는 IP와 주소는 **가상 기준정보**입니다. 현장에 연결할 때는 실제 값으로 바꿉니다.

### 1-2. 값이 신호가 되는 규칙

| 값의 변화 | 보내는 신호 | 서버에서 일어나는 일 |
|---|---|---|
| 가동 0 → 1 | RUN | 보류 · 대기 작업 재개(R5) |
| 가동 1 → 0 | STOP | 진행 중 작업 보류 |
| 누적 수량 증가 | COUNT(증가분) | 실적 저장(R6) |
| 이상 0 → 1 | FAULT | 고장 사건 등록 · 작업 보류(R1) |

프로그램을 처음 켰을 때 읽은 값은 기준으로만 삼고 신호를 보내지 않습니다. 누적 수량은 16비트 값이 65535에서 0으로 넘어가도 증가분을 바르게 계산합니다.

### 1-3. 전체 흐름

```
LS PLC ── Modbus TCP ──┐
                       ├─▶ bridge.py ─ HTTPS ─▶ tp_ingest_signal(출처 MODBUS·ETOS 기록) ─▶ 규칙 R1~R7 ─▶ DB ─▶ 화면 5개
ETOS ── XGT FEnet ─────┘
```

화면의 [설비 신호] 시뮬레이터도 같은 입구로 신호를 보냅니다. 출처는 SIM으로 기록됩니다. 그래서 현장을 연결해도 입구 뒤의 규칙 · DB · 화면은 바꿀 필요가 없습니다.

## 2. 준비물

- Python 3.9 이상. 이 폴더의 프로그램은 표준 라이브러리만 써서 따로 설치할 것이 없습니다.
- 서버에 `supabase_io.sql`이 적용되어 있어야 합니다. 신호 출처 기록과 수집 포인트 표가 여기에 들어 있습니다.
- 서버 주소, 공개 키, 시연 코드. 셋 다 파일에 쓰지 말고 환경 변수로만 넣습니다.

## 3. 시연 방법: 가상 장비로 실제 흐름 보여 주기

명령 창(Windows는 PowerShell)을 **두 개** 엽니다.

### 3-1. 첫 번째 창: 가상 현장 장비 켜기

```
cd tools/io_bridge
python field_sim.py
```

이 컴퓨터에 가상 장비가 뜹니다. LS PLC 5대(Modbus, 포트 15021~15028)와 ETOS 1대(포트 12004)입니다. `>` 표시가 나오면 아래 명령으로 장비 값을 바꿀 수 있습니다.

| 명령 | 뜻 |
|---|---|
| `count EQ05 10` | EQ05 누적 수량 +10 |
| `fault EQ01` / `clear EQ01` | EQ01 이상 비트 켜기 / 끄기 |
| `run EQ04` / `stop EQ04` | EQ04 가동 비트 켜기 / 끄기 |
| `show` | 지금 값 모두 보기 |
| `quit` | 종료 |

`python field_sim.py --auto 10`으로 켜면, 10초마다 가동 중인 장비의 누적 수량이 1씩 자동으로 오릅니다.

### 3-2. 두 번째 창: 연결 프로그램 켜기

**① 서버 정보 넣기(창을 열 때마다 한 번).** PowerShell 기준입니다.

```
$env:TP_SUPABASE_URL = "https://<프로젝트>.supabase.co"
$env:TP_SUPABASE_KEY = "<anon public 키>"
$env:TP_DEMO_CODE    = "<시연 코드>"
```

macOS · Linux에서는 `$env:이름 = "값"` 대신 `export 이름="값"`을 씁니다.

**② 실행하기.**

```
cd tools/io_bridge
python bridge.py
```

**③ 확인하기.** 첫 번째 창에서 `count EQ05 10`을 입력합니다. 두 번째 창에 `EQ05 MODBUS → COUNT 10`과 서버 응답이 찍히고, 화면에는 다음이 바로 나타납니다.

- **통합 관제:** 위쪽 「데이터 수집」 칩이 「연결 프로그램 수신(Modbus)」으로 바뀝니다.
- **설비 상태:** 신호 기록에 「Modbus」 배지가 붙습니다.
- **생산 현황 · 작업 관리:** 실적이 바뀝니다.

`fault EQ01`을 입력하면 고장 사건이 생깁니다. 작업 관리 카드의 감지 경로는 「Modbus FAULT 신호로 자동 등록」으로 나옵니다.

**④ 서버 없이 확인만 하기.** `python bridge.py --dry-run`으로 켜면 서버로 보내지 않고 창에만 출력합니다.

## 4. 현장에 연결할 때

1. `config_site.json`의 IP · 포트를 현장 값으로 바꿉니다. 각 설비 PLC의 IP는 `devices[].host`, ETOS의 IP는 `etos.host`입니다.
2. 기준정보의 수집 포인트(`tp_io_point`)도 같은 값으로 맞춥니다.
3. `python bridge.py --config config_site.json`으로 실행합니다.

현장 PLC의 실제 주소 배치(어느 Coil · 레지스터가 가동 · 수량 · 이상인지)가 다르면 `bridge.py`의 읽는 부분(`c.bit(1, 0)`, `c.bit(2, 0)`, `c.reg(0)`)과 ETOS `%MW` 번호(`mw`)를 현장 배치에 맞춥니다.

## 5. 자동 테스트

전체 소스 패키지(`twinpro_app`)의 최상위 폴더에서 실행합니다. 시연 저장소(`twinpro-demo`)에는 테스트용 로컬 서버가 없어 이 파일을 넣지 않았습니다.

```
node tools/io_bridge/test_bridge.js
```

이 테스트는 실제 서버 대신 같은 SQL을 올린 로컬 Postgres(PGlite)를 씁니다. 가상 장비, 연결 프로그램, 서버 입구까지 한 번에 돌린 뒤 다음 두 가지를 확인합니다.

- Modbus · ETOS 신호가 출처와 함께 기록되는지
- 고장 사건이 만들어지는지

## 6. 파일

| 파일 | 내용 |
|---|---|
| `bridge.py` | 연결 프로그램. Modbus TCP · XGT FEnet 읽기 → 신호 변환 → 서버 입구 호출 |
| `field_sim.py` | 가상 현장 장비. LS PLC 5대(Modbus TCP) · ETOS 1대(XGT FEnet) |
| `config_demo.json` | 시연용 설정. 이 컴퓨터(127.0.0.1)의 가상 장비를 읽음 |
| `config_site.json` | 현장용 예시 설정. 수집 포인트 표의 가상 IP |
| `test_bridge.js` | 자동 테스트. 가상 장비 → 연결 프로그램 → 로컬 서버 |
